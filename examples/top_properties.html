Press play. The engine starts at FROM, not at SELECT — that gap between written order and real order is the whole point.

What it catches

WARNFunction wrapped around a filter column
Inside CTE 'monthly': d.full_date is wrapped in a function inside WHERE, so the engine computes it per row and cannot range-scan the column. A start/end range rewrite is usually far cheaper.
WARNDISTINCT aggregate
Inside CTE 'monthly': COUNT(DISTINCT f.lease_id) forces its own distinct pass over the grouped rows before it can aggregate.
WARNWildcard select
Inside CTE 'ranked': a wildcard select drags every column into the next step, including columns nobody reads downstream.
INFOWindow functions
Inside CTE 'ranked': RANK run as window functions, computed after that query's grouping over partitions of its rows. Each partition and sort combination is another pass over the data.
INFOWindow functions
Inside CTE 'ranked': LAG run as window functions, computed after that query's grouping over partitions of its rows. Each partition and sort combination is another pass over the data.
INFOFilters are evaluated after the joins
In logical order, WHERE runs after the joins, so the joins conceptually carry unfiltered rows. Most optimizers push filters down automatically, but stacked views and some engines do not — worth knowing when a join feels slow.
INFOScalar subquery in SELECT
A (SELECT ...) sits in the select list. It is its own query with its own scan of its source. Engines usually evaluate a constant scalar subquery once, but it hides real work inside the SELECT list where nobody costs it.
INFOSort with no LIMIT
ORDER BY without LIMIT sorts the entire result set. If only the top rows matter, a LIMIT lets the engine use a much cheaper top-N sort.
Logical execution order, as taught by every SQL engine's documentation. QueryScope reads the query structure only — it does not connect to your database, and row counts depend on your data.
